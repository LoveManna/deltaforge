## 1. The 60-second version

This project tries to prove a hand-written Triton kernel can beat
`torch.compile(mode="max-autotune")` on `Qwen/Qwen3.5-4B` batch-1 decode — **and to say
where, by how much, and why, in advance.** The second half is the actual contribution.

Yesterday's batch 003 rented an RTX 5090 and produced **seven admissible ratios, all losses**.
The valuable part is that it produced the *cause* too:

* The compiled baseline runs at **1171-1308 GB/s, 66-73% of the card's 1790 GB/s peak.** The
  compiler is already near the memory wall.
* The hand-written GEMV reached **332 GB/s at bf16, 141 at int8, 65 at int4**. As it removed
  bytes it got *slower* — which is the signature of a kernel bound by instruction issue, not
  bandwidth, and it explains every number in the batch.
* The cause is one line: `acc += tl.sum(w * x[None, :], axis=1)` runs a cross-lane reduction
  **once per K-iteration** — 20× for K=2560, 72× for K=9216 — where the standard form
  accumulates a tile and reduces once.

**Batch 004 fixes that kernel, then quantises on top of it.** The plan is eight tasks.

## 2. The one number that decides everything

Define `f` = the candidate kernel's byte rate ÷ the compiled baseline's 1171 GB/s.

| `f` | GB/s | bf16 control ratio | int8/fp8 + LM head |
|---:|---:|---:|---:|
| **0.284** | **332** | **0.333** | 0.581 ← batch 003, measured |
| 0.50 | 585 | 0.562 | **1.000** |
| 0.73 | 850 | 0.761 | **1.40** |
| 1.00 | 1171 | 1.000 | **1.85** |

**The gate is `bf16 control ≥ 0.56`.** Below it, quantisation cannot even tie and the
batch's preconditions should fire. Do not loosen this if it fires — that is the batch working.

**Required improvement is 1.8×, not 4×.** This is why the plan is worth executing.

## 7. Traps specific to this work

Read `AGENT.md` §8 in full. The four that will bite *this* plan:

1. **`tl.dot` needs `BLOCK_N ≥ 16` and `BLOCK_K ≥ 16`.** You cannot narrow the tile to buy
   parallelism the way batch 003's kernel did. Split-K is the instrument instead.
2. **`in_proj_a` and `in_proj_b` are 32 output channels wide.** No tile choice fills a card.
   They are 0.03% of bytes, so it does not matter much — but a plan that forgets them will
   produce a confusing slow site.
3. **Do not run `triton.autotune`.** Its trials fire on the first call, which under CUDA-graph
   capture is exactly the wrong moment. Every kernel here sizes its launch deterministically.
4. **Widening a batch means widening dynamo's recompile limit.** `recompile_limit_for` derives
   it from the slot count, so it is automatic — but check `graphs_compiled` is non-zero in
   every slot record before believing any ratio. A `0` there means that number is not a
   comparison. This cost rental 35 six of nine slots.

## 8. Known-unknowns you are inheriting

State these honestly in the writeup rather than resolving them by assertion.

* **Why did `010-int8-dequant-torch` move 39% fewer bytes for 0% less time?** Measured 0.9893
  ± 0.0212. The naive "inductor materialises the weight" story is refuted — it would need
  2525 GB/s on a 1790 GB/s card — so inductor either fuses the dequant into the matmul
  prologue or keeps the transient in the 96 MB L2. **Task 7's `output_code` dump is what
  answers this**, and it is the free diagnostic `docs/HYPOTHESES.md` calls mandatory and
  batch 003 skipped.
* **Where does the baseline's remaining 27% go?** Nobody knows. It is a 1.37× hypothesis.
* **Does inductor fold the GQA `repeat_interleave`?** `docs/HYPOTHESES.md` entry 2 has been
  conditional on this since it was written and it has never been checked.
